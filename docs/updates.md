# 主分支开发与自动更新

用户已确认独自开发，后续直接提交 `main`。首个原型PR已合并；不再为日常修改建立开发分支或PR。

## 使用方式

首次从 [最新Release](https://github.com/XiminHu66/toy-dg/releases/latest) 下载
`toy-dg-launcher.zip`，解压后固定使用 `ToyDG-Launcher.exe` 启动。
也可使用[固定下载链接](https://github.com/XiminHu66/toy-dg/releases/latest/download/toy-dg-launcher.zip)。

启动器联网获取版本清单，有新版本时自动下载、校验、安装，完成后点击“开始游戏”。
首次安装需要网络；已有版本时检查失败仍可启动旧版。旧的单文件游戏客户端没有启动器，
因此需要切换下载一次，之后常规游戏更新不再需要人工下载、解压和覆盖。

## 更新流程

1. `main`提交触发Godot导入、规则／存档／更新器测试及界面冒烟检查。
2. 导出Web、Windows游戏与Windows启动器。
3. Windows runner实际运行游戏和启动器冒烟测试，通过后才发布Release。
4. 构建清单记录版本、源码提交、包大小、包SHA-256，以及每个解压文件的大小与SHA-256。
5. 先建立Release草稿，上传全部文件，再发布并设为latest，避免用户看到半成品。
6. 启动器读取固定HTTPS地址，下载到临时文件；完整校验通过后才切换当前版本。
7. 发布后再在Windows runner实际验证“联网检查→下载→安装→运行下载的游戏”全链路。

版本号当前为 `0.1.<工作流运行编号>`，编号可能有间隔，不表示每天固定更新。
每次主分支通过验证的构建都可成为新版本。已发布的同版本文件不被工作流重跑覆盖。

## 安装和存档

启动器和游戏沿用相同项目用户目录，但更新内容只写入其 `updates/` 子目录。
游戏的 `profile.json` 与备份仍位于原来的用户目录，更新器不读写或删除它们。
Windows默认位置可在 `%APPDATA%/Godot/app_userdata/地城拾遗 · Toy Dungeon/` 找到。

每个版本安装在独立目录，旧版本保留；不覆盖正在运行的exe。
下载失败、哈希不匹配、文件不完整或非法压缩路径均不激活新版本。
“回退上一版本”切换到上一份仍通过校验的安装，并跳过这次问题版本，直到有更高版本发布。
这是手动回退，不是自动识别所有游戏崩溃。旧安装暂不自动清理，可能逐步占用磁盘空间。

游戏存档格式升级仍需单独实现迁移；保留存档文件不等于任意旧版都能读取新版存档。
当前原型存档格式未改变。

## 边界

- 首版下载完整Windows游戏包，通常几十MB；实现“自动更新”，暂不做二进制增量下载。
- 游戏引擎升级也随新版本exe分发，不受只更新PCK的引擎兼容限制。
- 当前更新源是公开的GitHub Release，不需要用户账号或令牌；不把凭据嵌入客户端。
- HTTPS和SHA-256用于固定来源及完整性校验，不等于独立发布签名或Windows代码签名。
- 启动器程序本身暂不自我替换。未来如必须改变启动协议，可提高清单中的minimum_launcher，
  届时提示更新启动器；当前常规玩法更新不需要更换启动器。
- 源码仓库可见性仍为Public，未更改。改为私有会影响匿名自动更新，需要另行调整更新源。
- 没有新增游戏服务器、云存档或账号体系；联网只用于检查与下载。
- 网页版可通过部署新版本实现打开时更新，但本项目当前仍只有Web导出包，尚未开通在线托管。

## 开发验证

`python3 scripts/ci_check.py` 包含更新器测试。可通过环境变量GODOT指定编辑器路径。
`--launcher-smoke`只验证启动器界面且不联网；`--launcher-update-test`仅用于Windows CI，
使用隔离的安装目录验证公开Release下载和游戏启动，不是普通玩家启动参数。

`scripts/package_release.py <version> <commit>`打包已导出的文件并生成update.json。
Windows游戏包包含且仅包含toy-dg.exe、THIRD_PARTY_NOTICES.md和OFL.txt。
